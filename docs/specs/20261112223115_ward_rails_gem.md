# Gem ward-rails — secrets do ward no runtime do app Rails

> **TLDR**: gem Rails 8 que lê o vault ward no boot (binário `ward` com saída `--json`, instalado por rake task) e expõe os segredos num store privado em memória (`Ward[...]`), sem nada em ENV — falha rápido com erro claro quando o contexto não carrega.

# what

Como dev Rails, quero que meu app consuma os secrets do ward diretamente no runtime (sem o step de sync do deploy para o runtime store), para ter o ward como fonte única dos segredos e poder rotacionar sem redeploy — com uso simples, opções de configuração, e o mínimo de exposição se o processo for comprometido.

O gem (a) instala o binário `ward` via `bin/rails ward:install` (versão pinada, checksum verificado), (b) no boot carrega o escopo de contexto definido por `WARD_CONTEXT` (ex: `secrets.main.code.production`) para um store privado e imutável, (c) expõe leitura avulsa de qualquer secret fora do contexto desde que a chave do vault esteja disponível, e (d) falha o boot com erro claro e acionável quando contexto, chave ou binário faltam (configurável para warning).

## out of scope

- Publicação no rubygems — uso via `gem "ward-rails", github: "br4zz4/ward-rails"` em CI
- Suporte a Rails < 8 e Ruby < 3.2
- Sidecar/processo isolado de decriptação (defesa contra dump de memória) — documentado como limite explícito, não como promessa
- Recarga automática em dev (só `Ward.reload!` manual)
- Escrita de secrets pelo gem (`set`/`unset`/`import`)
- Backfill automático de secrets em ENV
- Integração com `make setup`/bootstrap nos projetos consumidores (adotado projeto a projeto depois)
- Suporte a Windows

## acceptance criteria

### Boot e contexto

```gherkin
Cenário: app sobe com contexto válido
  Dado que WARD_CONTEXT=secrets.main.code.production está definida
  E as chaves dos vaults necessários estão disponíveis
  E bin/ward existe em Rails.root/bin/ward
  Quando o app termina o boot
  Então Ward["RESEND_API_KEY"] retorna o valor do vault
  E ENV não contém nenhum valor de secret carregado

Cenário alternativo: WARD_CONTEXT ausente
  Dado que WARD_CONTEXT não está definida
  Quando o app sobe
  Então o boot falha com Ward::MissingContext
  E a mensagem mostra um exemplo de contexto e onde definir a variável

Cenário alternativo: contexto não carrega (vault sem chave)
  Dado que WARD_CONTEXT está definida
  E a chave do vault que contém o contexto está ausente
  E config.ward.on_error é :raise (default)
  Quando o app sobe
  Então o boot falha com Ward::LoadFailed
  E a mensagem nomeia o vault e a chave que falta (ex: WARD_KEY_MAIN)

Cenário alternativo: on_error=:warn
  Dado que o contexto não carrega
  E config.ward.on_error é :warn
  Quando o app sobe
  Então o boot segue com store vazio e um warning no log com o motivo

Cenário alternativo: conflito entre vaults
  Dado que dois vaults definem a mesma chave no contexto
  Quando o app sobe
  Então o boot falha com Ward::LoadFailed (sem escolher vencedor)

Cenário alternativo: binário ward ausente
  Dado que bin/ward não existe
  Quando o app sobe com WARD_CONTEXT definida
  Então o boot falha com Ward::BinaryNotFound
  E a mensagem indica bin/rails ward:install (e WARD_BIN como alternativa)
```

### Store e API

```gherkin
Cenário: leitura de secret do contexto
  Dado que o store foi carregado no boot
  Quando chamamos Ward["RESEND_API_KEY"]
  Então retorna o valor exato do vault
  E o valor está congelado (frozen)

Cenário alternativo: chave ausente no store
  Dado que "NAO_EXISTE" não está no contexto
  Quando chamamos Ward["NAO_EXISTE"]
  Então retorna nil

Cenário alternativo: fetch com erro claro
  Dado que "NAO_EXISTE" não está no contexto
  Quando chamamos Ward.fetch("NAO_EXISTE")
  Então levanta Ward::MissingSecret
  E a mensagem lista as chaves disponíveis (nomes, nunca valores)

Cenário: acesso method-style
  Dado que o store tem a chave resend_api_key
  Quando chamamos Ward.secrets.resend_api_key
  Então retorna o mesmo valor de Ward["resend_api_key"]

Cenário alternativo: inspect não vaza valores
  Dado que o store está carregado
  Quando inspecionamos o store (inspect, p, log)
  Então a saída mostra os nomes das chaves e nunca os valores
```

### Leitura avulsa fora do contexto

```gherkin
Cenário: leitura por caminho qualificado
  Dado que o app roda no contexto secrets.main.code.production
  E WARD_KEY_COMMONS está disponível (via config.ward.keys)
  Quando chamamos Ward["commons:secrets.main.deploy.staging.TF_VAR_api_url"]
  Então retorna o valor do vault commons
  E a leitura é memoizada para o resto do processo (sem nova invocação do binário)

Cenário alternativo: vault sem chave na leitura avulsa
  Dado que a chave do vault commons não está disponível
  Quando chamamos Ward["commons:secrets.main.deploy.staging.TF_VAR_api_url"]
  Então levanta Ward::KeyUnavailable
  E a mensagem nomeia o vault e a chave que falta (ex: WARD_KEY_COMMONS)

Cenário alternativo: segredo TOTP
  Dado que o vault tem um segredo otpauth://
  Quando o gem lê esse segredo (boot ou avulsa)
  Então recebe o valor original (flag --raw), nunca o código de 6 dígitos
```

### Chaves

```gherkin
Cenário: chaves via config.ward.keys
  Dado que config.ward.keys = { "main" => Rails.application.credentials.ward_main_key }
  Quando o app sobe e lê secrets
  Então a chave é injetada apenas no subprocesso ward
  E ENV do app nunca contém WARD_KEY_MAIN
  E valor String é tratado como a chave direta; Symbol (ex: :WARD_KEY_MAIN) é tratado como nome de env var resolvido no momento da leitura; callable é chamado por leitura

Cenário alternativo: default herda ENV do processo
  Dado que config.ward.keys não foi definido
  E WARD_KEY_MAIN está no ENV do processo
  Quando o app sobe
  Então a chave chega ao subprocesso por herança do ambiente
```

### Installer

```gherkin
Cenário: instalação pinada com checksum (macOS e Linux)
  Dado que ward ainda não está instalado
  Quando rodamos bin/rails ward:install
  Então baixa ward v0.4.0 (WARD_MIN_VERSION) para a plataforma atual (darwin/linux × amd64/arm64)
  E verifica o sha256 contra checksums.txt antes de instalar
  E instala bin/ward com permissão de execução

Cenário alternativo: checksum divergente
  Dado que o download não confere com o checksum
  Quando rodamos bin/rails ward:install
  Então aborta com Ward::ChecksumMismatch
  E nenhum bin/ward parcial é deixado no disco

Cenário alternativo: reinstalação
  Dado que bin/ward já existe
  Quando rodamos bin/rails ward:install
  Então substitui o binário de forma atômica e idempotente

Cenário alternativo: plataforma não suportada
  Dado que o sistema não é darwin/linux amd64/arm64
  Quando rodamos bin/rails ward:install
  Então falha com Ward::UnsupportedPlatform e mensagem clara
```

### ward CLI (repo br4zz4/ward — dependência)

```gherkin
Cenário: secrets --json
  Dado que um projeto ward tem o vault configurado
  Quando rodamos ward --raw secrets --json secrets.main.code.staging
  Então stdout é um objeto JSON chave→valor
  E as chaves são as mesmas do `ward secrets` (leaf names, ou paths com --prefixed)

Cenário alternativo: get --json
  Quando rodamos ward --raw get --json vault:path.do.secret
  Então stdout é {"path": "...", "value": "..."}
  E um subtree é recusado com exit != 0

Cenário alternativo: --json em AI mode é recusado
  Dado que WARD_AI_MODE=1 (ou --ai-mode)
  Quando rodamos qualquer comando com --json
  Então o comando falha e nenhum valor é exposto

Cenário alternativo: falha não emite JSON parcial
  Dado que a chave do vault está ausente
  Quando rodamos ward --raw secrets --json <scope>
  Então o exit status é diferente de zero, stderr tem a explicação e stdout não contém JSON
```

# why

- **Fonte única em runtime**: hoje o deploy sincroniza ward → runtime store → env vars, duplicando segredos em dois lugares e criando drift; rotação exige rodar o pipeline. Ler o vault direto elimina o step de sync e o risco de valor velho no runtime store.
- **Rotação sem redeploy**: segredo rotacionado no vault vale no próximo boot; leituras avulsas valem na hora (memoização por processo).
- **Devs locais no mesmo caminho**: produção, staging e máquina local usam exatamente o mesmo mecanismo (`WARD_KEY_*` + `WARD_CONTEXT`), sem fluxo especial de dotenv.
- **Segurança como default, não como opção**: segredos nunca vão para ENV global (vetor clássico de RCE — legível por qualquer gem e child process); store privado com valores congelados e `inspect` redacted; chaves nunca aparecem em log; falha no boot evita app "meio vivo" rodando com metade dos segredos.
- **Uso simples**: uma rake task instala o binário e um initializer curto configura tudo; `Ward["NOME"]` é a API inteira do dia a dia.

# how

A entrega tem um PR no repo `br4zz4/ward` (dependência — saída `--json`) e quatro PRs empilhados no `ward-rails`. O gem só funciona com ward ≥ v0.4.0 (versão pinada em `Ward::WARD_MIN_VERSION`).

## PR 0 — ward: saída JSON em secrets/get (branch: `feat/json-output`, base: `main` do br4zz4/ward)

**Entrega:** flags `--json` em `secrets` e `get`; recusa de `--json` em AI mode; contrato de saída estável para o gem.

**Arquivos:** Modify `internal/cmd/secrets.go`, `internal/cmd/get.go`, `README.md`, `docs/configuration.md` — Create `test/e2e/json/json_test.go`

**Contrato (o gem depende disso):**
- `ward --raw secrets --json [scope...]` → stdout = objeto JSON `{"<leaf_name>": "<value>", ...}`; os nomes são exatamente os mesmos da tabela do `ward secrets` (sem transformação de caixa); `--prefixed` continua valendo; valores nunca truncados.
- `ward --raw get --json <path>` → stdout = `{"path": "<path>", "value": "<value>"}`; um subtree é recusado.
- `--json` combinado com AI mode (`--ai-mode` ou `WARD_AI_MODE=1`) → erro, nenhum valor emitido.
- Qualquer falha: exit != 0, stderr com explicação, stdout sem JSON.

**Passos (TDD):** testes e2e que falham (`test/e2e/json/json_test.go`) → implementação mínima → testes verdes → commit `feat: json output for secrets and get`.

**Valida:** `go test ./...` e `go build ./...` no repo ward; manual: `ward --raw secrets --json <scope>`.

**Pronto para prod:** flag nova; sem `--json` o comportamento é idêntico ao atual. Publicar release **v0.4.0** (tag → goreleaser) antes do PR 2 do gem (o CI baixa essa versão).

## PR 1 — ward-rails: esqueleto do gem + Store + Loader (branch: `feat/ward-rails-1`, base: `main`)

**Entrega:** gem carregável com o núcleo puro (Store imutável, Loader de subprocesso, erros, fachada `Ward`) — sem comportamento automático em boot (Railtie vem no PR 3), então apps existentes não mudam.

**Arquivos:** Create `ward-rails.gemspec`, `Gemfile`, `Rakefile`, `lib/ward-rails.rb`, `lib/ward.rb`, `lib/ward/errors.rb`, `lib/ward/store.rb`, `lib/ward/loader.rb`, `test/test_helper.rb`, `test/ward/store_test.rb`, `test/ward/loader_test.rb`, `test/fixtures/bin/fake-ward`

**Passos (TDD):**
1. `test/ward/store_test.rb` falhando: valores `dup.freeze`; `fetch` levanta `MissingSecret` listando só nomes; `[]` retorna nil; `method_missing` para `Ward.secrets.x`; `inspect` não contém valores.
2. Implementar `Ward::Store` + `Ward::Errors` (hierarquia: `Ward::Error` ← `MissingContext`, `BinaryNotFound`, `LoadFailed`, `MissingSecret`, `KeyUnavailable`, `ChecksumMismatch`, `DownloadFailed`, `UnsupportedPlatform`).
3. `test/ward/loader_test.rb` falhando com `test/fixtures/bin/fake-ward` (script executável que imita o contrato JSON): sucesso (parse do objeto), exit != 0 (mapeia para `LoadFailed`/`KeyUnavailable`), stdout inválido (erro, sem incluir stdout na mensagem).
4. Implementar `Ward::Loader`: `Open3.capture3(env, bin, "--raw", cmd, "--json", *args, "-d", dir)`; env de chaves injetado por invocação; stdout **nunca** embutido em mensagens de erro (só exit status + stderr truncado); memoização sob `Mutex` para leituras avulsas.
5. `lib/ward.rb`: `VERSION`, `WARD_MIN_VERSION = "0.4.0"`, `[]`, `fetch`, `secrets`, `key?`, `loaded?`, `reload!`, `reset!` (testes junto).

**Valida:** `bundle exec rake test`.

**Pronto para prod:** o gem é requireável e a API funciona chamada manualmente; nada é executado automaticamente sem a Railtie.

## PR 2 — ward-rails: Installer + rake task (branch: `feat/ward-rails-2`, base: `feat/ward-rails-1`)

**Entrega:** `bin/rails ward:install` baixa o binário pinado com checksum verificado e instala em `bin/ward`.

**Arquivos:** Create `lib/ward/installer.rb`, `lib/tasks/ward.rake`, `test/ward/installer_test.rb`

**Passos (TDD):**
1. `test/ward/installer_test.rb` falhando (servidor HTTP local com WEBrick servindo fixture tarball + checksums.txt): plataforma correta resolvida por `RbConfig::CONFIG` (darwin/linux × arm64/amd64; x86_64→amd64, aarch64→arm64); checksum divergente → `ChecksumMismatch` e nenhum arquivo parcial; extração com `Gem::Package::TarReader` + `Zlib::GzipReader`; instalação atômica (tmp → rename) com `chmod 0755`; reinstalação idempotente; plataforma não suportada → `UnsupportedPlatform`.
2. Implementar `Ward::Installer` (download de `https://github.com/br4zz4/ward/releases/download/v<WARD_MIN_VERSION>/ward_<os>_<arch>.tar.gz` + `checksums.txt`; sha256 via `Digest::SHA256`; verificação antes de mover; imprime `ward version` ao final).
3. `lib/tasks/ward.rake` — task fina sobre o Installer.

**Valida:** `bundle exec rake test`; execução real `bundle exec rake ward:install` (macOS local e CI Linux).

**Pronto para prod:** a task existe e é independente; nada a invoca automaticamente.

## PR 3 — ward-rails: Railtie + Configuration + boot (branch: `feat/ward-rails-3`, base: `feat/ward-rails-2`)

**Entrega:** o gem passa a carregar o contexto no boot de apps Rails, com fail-fast configurável — é o PR que liga a funcionalidade.

**Arquivos:** Create `lib/ward/configuration.rb`, `lib/ward/railtie.rb`, `test/ward/railtie_test.rb`, `test/dummy/` (app Rails mínima), `test/fixtures/ward_project/` (projeto ward real gerado com o binário: `.ward/config.yaml` + vault + age key de teste)

**Comportamento:**
- `Ward::Configuration` (via `Rails.application.config.ward`): `context` (default `ENV["WARD_CONTEXT"]`), `keys` (hash vault → `String` valor direto, `Symbol` nome de env var resolvido na leitura, ou callable; default: herdar ENV do processo), `bin` (default `Rails.root/bin/ward`, `WARD_BIN` sobrescreve), `on_error` (`:raise` default, `:warn` alternativo), `dir` (default `Rails.root`).
- Railtie registra `config.after_initialize`: (1) contexto ausente → `MissingContext` com exemplo (`secrets.main.code.production`) e onde definir; (2) binário ausente → `BinaryNotFound` apontando `bin/rails ward:install`; (3) roda `ward --raw secrets --json <context> -d dir`; (4) store resultante **vazio** → `LoadFailed` (cobre vault sem chave e conflito, que já saem com exit != 0); (5) `on_error == :warn` → loga warning e segue com store vazio.
- Leitura avulsa: `Ward["vault:path"]` (contém `:`) → `ward --raw get --json` memoizado; falha → `KeyUnavailable` nomeando o vault e a chave esperada (ex: `WARD_KEY_COMMONS`).
- Chaves: `config.ward.keys` são injetadas **só** no env do subprocesso; nunca tocam o ENV do app; nunca aparecem em log.

**Passos (TDD):** `test/ward/railtie_test.rb` falhando com a dummy app + fixture ward real (boot carrega valores; sem `WARD_CONTEXT` falha; `on_error=:warn` segue vazio; leitura avulsa com e sem chave; ENV do app sem secrets e sem chaves injetadas) → implementação mínima → verdes.

**Valida:** `bundle exec rake test` (o CI instala ward v0.4.0 real antes); manual: `WARD_CONTEXT=secrets.main.code.production bundle exec rails runner 'puts Ward.keys'` num projeto consumidor.

**Pronto para prod:** apps que não adicionam o gem não mudam; apps que adicionam sem `WARD_CONTEXT` falham rápido com mensagem acionável.
